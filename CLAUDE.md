## Product summary

Nouttbuk is a note-taking app for university students that combines a private, per-subject note library with an academic community feed. The single core mechanic is that every note (`apunte`) has a visibility level set individually: `private` (owner only), `group` (owner + invited collaborators with `read`/`edit` permission), or `community` (publishes to a public feed, readable without login; this is the growth/SEO hook and must never be regressed). Reactions and saves on community posts are per-user rows, not global counters.

MVP is scoped to a single university (Pontificia Universidad Católica del Perú): signup is rejected unless the email ends in `@pucp.edu.pe`, enforced both client-side (`src/lib/auth/dominio-institucional.ts`) and at the database level (trigger in `supabase/migrations/20260817204401_auth_domain_restriction.sql`). Multi-university support is explicit v2.0 scope (see `STACK.md`).

## Stack

Next.js 16 (App Router, TypeScript) + Supabase (Postgres/Auth/Storage/Realtime) + Tailwind CSS v4 + shadcn/ui (`base-nova` style, over `@base-ui/react`, **not** Radix) + Tiptap v2 (editor; pinned below v3 because `@liveblocks/react-tiptap` requires Tiptap v3 and this project uses a manual Yjs integration instead, see the Liveblocks note below) + Liveblocks (`@liveblocks/client`/`react`/`yjs`/`node`, real-time co-editing for `group`-visibility notes with `edit` permission) + Motion (motion.dev, everyday micro-interactions) + anime.js v4 (a few signature moments, e.g. the Comunidad hero) + jsPDF (client-side CV PDF generation, dynamically imported) + Cloudflare Turnstile (CAPTCHA on signup/login/recover, code-complete but shipped disabled pending real credentials) + Phosphor icons (`@phosphor-icons/react`) + Vercel (not yet deployed).

All four `@liveblocks/*` packages must be pinned to the exact same minor version; mixing majors (e.g. `@liveblocks/node@^3` against `@liveblocks/client@2.24.4`) loads two incompatible copies of `@liveblocks/core` and Liveblocks throws a runtime "dupes" error.

The visibility model (`private`/`group`/`community`) is enforced via Postgres **Row Level Security**, not hand-rolled authorization checks in application code. Public feed reads and authenticated writes (react/save/comment/create) are designed as separate query/mutation paths.

## Architecture

**Supabase client pattern** (`src/lib/supabase/`): three separate client factories, standard `@supabase/ssr` split — `client.ts` (browser, used from Client Components and the auth forms), `server.ts` (reads/writes cookies via `next/headers`, used from Server Components/route handlers), `middleware.ts` (`updateSession`, refreshes the session cookie on every request). `middleware.ts` is wired in via `src/proxy.ts` (Next.js 16's replacement for the old `middleware.ts` convention at the project root) — it only refreshes cookies, it does not redirect; route protection happens in each gated page, not centrally.

**Route structure** (`src/app/`): a `(shell)` route group holds the four nav destinations behind one shared layout. `(shell)/layout.tsx` is a Server Component that reads the session once (`auth.getUser()` + a `profiles` lookup) and passes it as a plain prop to `AppShell` (`src/components/nav/app-shell.tsx`, a Client Component that owns nav state and the auth modal). Deliberate decision: `(shell)/page.tsx` (`/`) is the public Comunidad feed with **no auth check**, so it can never accidentally end up gated behind a login wall — this is the SEO/growth-hook route from the product rules above. `/inicio`, `/apuntes`, `/perfil` are Server Components that call `redirect("/?login=1")` when there's no session; `AppShell` reads that query param in an effect (keyed on `pathname`, not mount, since a server-side redirect during a client navigation reuses the existing shell instance instead of remounting it) and auto-opens the login modal.

**Design tokens** (`src/app/globals.css`): the Tailwind v4 `--radius-*` scale is *not* derived from a single multiplier — cards/dialogs/sheets need 26px (`--radius-xl`) and buttons/inputs/selects need 14px (`--radius-lg`) simultaneously, which a single-base chain can't produce, so each step of the scale is set to an explicit value. Colors follow DESIGN-SYSTEM.md's Indigo/Teal/Slate tokens with distinct light/dark values (not auto-inverted).

**Icons**: `@phosphor-icons/react`'s default export needs a client boundary (it isn't RSC-safe); the package ships a separate `@phosphor-icons/react/dist/ssr` entry that is. Use the plain import inside Client Components (shadcn-generated `src/components/ui/*` and anything under `src/components/nav/`, `src/components/auth/`), and the `/dist/ssr` import inside Server Components (the gated route pages in `src/app/(shell)/*/page.tsx`).

**shadcn/ui components** (`src/components/ui/`): generated via `npx shadcn add <name>` using this project's `base-nova` style (`components.json`, `iconLibrary: "phosphor"`) over `@base-ui/react` primitives — the generated API shape (prop names, `render` prop patterns, `data-slot` attributes) follows Base UI conventions, not Radix's, even though it looks similar. Check a freshly-generated file's actual output before assuming an API from Radix-based shadcn docs.

**Auth forms** (`src/components/auth/`): `login-form.tsx`, `signup-form.tsx`, `recuperar-form.tsx` are composed inside `auth-modal.tsx` (a fully controlled `mode`/`open` component, no internal state), all reachable from `AppShell`. Supabase Auth error messages are normalized to Spanish copy in one place, `src/lib/auth/mapear-error-auth.ts` (tested in `tests/mapear-error-auth.spec.ts`), rather than string-matched inline in each form. Signup passes `nombre`/`usuario`/`carrera` via `signUp({ options: { data: {...} } })`; it never inserts into `profiles` directly, that row is created by the `handle_new_user` DB trigger.

**Auth gate outside the shell's redirect-based flow** (`src/components/nav/auth-gate.tsx`): `AuthGateProvider`/`useAuthGate()` wraps the shell's `<main>`, reusing `AppShell`'s existing `abrirAuth("login")` closure. Gated *pages* (`/inicio`, `/apuntes`, `/perfil`) use the `redirect("/?login=1")` + query-param mechanism described above, but content that's optionally-authenticated on an otherwise-public page (Comunidad's reaccionar/guardar/comentar) can't rely on that, since the page itself never redirects. Any component under the shell can call `useAuthGate().abrirLogin()` to open the login modal from wherever it's rendered.

**Aggregate counts blocked by RLS** (`get_publicacion_counts`, `get_perfil_stats`, migrations in `supabase/migrations/`): when a screen needs a count across *other* users' rows that RLS won't let the caller read directly (e.g. reactions received on your own publications, or public reaction counts for `anon`), the pattern is a narrow `security definer set search_path = '' stable` SQL function living in `public` (not `private`, which is reserved for internal RLS-policy helpers), granted only to the roles that actually need it (`anon, authenticated` for feed-facing counts, `authenticated` only for own-profile stats — never bare `grant ... to public`). Don't reach for client-side joins or loosen RLS instead.

**Sheet vs. full-screen overlay**: two distinct overlay patterns, chosen by how much the screen holds, not by how it's reached. Small single-entity edits (`carpeta-sheet.tsx`, `editar-perfil-sheet.tsx`) use `Sheet`/`SheetContent(side="bottom")` from `src/components/ui/sheet.tsx`, with local `open`/`cargando`/`error` state and `router.refresh()` on success. Full destinations (`apunte-editor.tsx`, `detalle-publicacion.tsx`) render a plain `fixed inset-0 z-50` div from a normal route inside `(shell)`, instead of a nested layout, so they cover the sidebar nav without a second route tree.

**Recurring gotchas**: Tiptap's `useEditor()` needs `immediatelyRender: false` (otherwise an SSR hydration mismatch, since ProseMirror needs the real browser DOM). Base UI's `Select` needs an `items` prop (not just `SelectItem` children) or the closed trigger shows the raw value instead of the item's label. A component that seeds `useState` from an optional prop needs a `key` tied to that prop's identity, or it goes stale when the prop changes without the component unmounting. A PostgREST embed between two tables with more than one relationship path (e.g. `apuntes`↔`profiles` via both `autor_id` and `colaboradores`) needs the explicit FK name (`profiles!apuntes_autor_id_fkey`), or the query silently returns `PGRST201`. RLS policies alone aren't enough for a new table: Postgres checks table-level `GRANT`s first, so every RLS-protected table also needs a matching grant (see `supabase/migrations/20260818053857_table_grants.sql`), and this must be considered explicitly even for the `anon` role on a table `anon` has no RLS policy on at all, otherwise a missing grant surfaces as a hard permission-denied error instead of the intended RLS-driven empty result (hit twice in this project's history). A flex container with no explicit `align-items` defaults to `stretch`, which silently caps a `min-h-[...]`-only child's height at the container's own computed height instead of letting it grow with content (bit the editor's A4 "hoja" once); add `items-start` when a child should size to its content. pgTAP's `throws_ok(sql, errcode, description)` matches its third argument against the actual Postgres exception message, not a free-text description, unless a 4th argument is passed. There is no admin role anywhere in this app: status/moderation changes (`feedback.estado`, reviewing rows in `reportes_publicacion`/`reportes_comentario`) are done by hand via SQL or Supabase Studio, not a built UI, by design.

## Language rule for all user-facing text

All copy (UI strings, error messages, docs, comments, and any reply written in this project) must be in **neutral/standard Spanish** ("tú" forms). Never Rioplatense/Argentine Spanish (no "vos", no voseo conjugations like "tenés"/"podés"/"hacé"). This has been corrected multiple times in this project; treat it as a hard constraint, not a style preference, and re-check any generated string against it before finalizing. Also avoid em dashes as a sentence/clause separator, use commas or split sentences instead; this is a separate, equally strong standing preference in this project.

### Calendario (`todo.md` post-MVP item, new nav destination)

**Data model** (`supabase/migrations/20260904140544_calendario.sql`, `supabase/tests/database/38_calendario.test.sql`): `bloques_horario` (perfil_id, título, `dia_semana` 0=lunes..6=domingo — deliberately not ISO/JS `Date.getDay()` numbering, and not real dates: a student's schedule is a **recurring weekly pattern**, not calendar events on specific dates, which is also what makes "does everyone have this same time free every week" answerable at all) + `hora_inicio`/`hora_fin` (Postgres `time`, with a `check (hora_fin > hora_inicio)` constraint) + `color` (reuses `COLORES_CARPETA` from `src/lib/carpetas/colores.ts` as-is, no new palette). `calendario_colaboradores` (propietario_id, colaborador_id) is the sharing table, **unidirectional by design**: sharing your calendar with someone lets them see your blocks (needed to compute overlap), it does not give you access to theirs or let them re-share yours — same "owner administers their own row, invitee can't touch it" shape as `colaboradores` for apuntes, confirmed by a pgTAP test that specifically checks the invitee can't delete the owner's blocks or revoke their own access. RLS: `bloques_horario` is selectable by its own `perfil_id` OR anyone in `calendario_colaboradores` for that owner; only the owner can insert/update/delete (`for all ... using (perfil_id = auth.uid())`). Both tables' grants are in the same migration file (the project's established "self-contained migration" pattern from `20260820100000_tables_feedback.sql` onward, not appended to the old central `20260818053857_table_grants.sql`). **A pgTAP `throws_ok` gotcha hit and fixed**: a 3-argument `throws_ok(sql, errcode, description)` call does NOT treat the third string as a free-text description — it's matched against the *actual* exception message, so a plain `check` constraint's own generic Postgres message ("new row for relation ... violates check constraint ...") had to be spelled out verbatim as that argument, with the real description moved to a 4th argument. Worth remembering for any future test on a plain `check` constraint (as opposed to a `raise exception` with a custom message, which is what every other `throws_ok` call in this project's test suite up to now was written against).

**Query layer** (`src/lib/calendario/consultas.ts`): `DIAS_SEMANA` (the day-index-to-label array, single source of truth for the 0=lunes numbering), `consultaBloquesDe(perfilIds[])` (fetches every block for a set of people in one call — used for both "my own calendar" with a one-element array, and the merge view with `[self, ...everyone who shared with me]`, since RLS already scopes exactly to what the viewer can legitimately see), `consultaCalendariosCompartidosConmigo`/`consultaConQuienComparto` (the two directions of the sharing table, joined to `profiles` via the explicit-FK pattern this project always needs for that table).

**Merge/overlap math** (`src/lib/calendario/grilla.ts`, pure functions, no React): the grid is 7:00-22:00 in 30-minute slots (`TOTAL_FRANJAS` = 30). `filaInicio`/`filasSpan` convert a block's `hora_inicio`/`hora_fin` into 1-indexed CSS grid row coordinates, clamped to the visible grid so a block starting before 7:00 doesn't produce a negative row index. `franjasOcupadas(bloques[])` returns a `Set<"dia:franja">` of every slot covered by at least one of the given blocks (the union across everyone selected — a slot only counts as free if *nobody* in the selection is busy then). `rangosLibresPorDia(dia, ocupadas)` walks the 30 slots and groups consecutive free ones into human-readable ranges (`{inicio, fin}` as "HH:MM" strings) — this is the direct answer to "when can everyone meet," not just a color-coded grid a person has to visually scan. **Verified correct with real data, not just reasoning about the code**: two throwaway accounts each created one block (08:00-09:00 and 08:30-10:00, both Monday), shared calendars with each other, and the merge view showed exactly "Lunes: 07:00–08:00, 10:00–22:00" as free — the union of the two blocks (08:00-10:00) subtracted correctly.

**UI**: `calendario-semana.tsx` (the grid itself, one component with two modes — `perfilId` present = interactive owner view with a `BloqueSheet` per day column as an invisible full-column "add" trigger (hover to reveal a `+`, clicking anywhere in the day opens a blank sheet pre-filled to that day) plus each block itself being a clickable `BloqueSheet` trigger for editing; `perfilId` absent = read-only merge view, background slot tinting from `franjasOcupadas`, and each block labeled by its *owner's name* instead of its title — deliberately, so a friend's "Cálculo 2" doesn't leak the exact course name to everyone in the merge, only "busy, and here's whose"). `bloque-sheet.tsx` (create/edit/delete a block, same Sheet+nested-Dialog-for-delete shape as `apunte-opciones-menu.tsx`'s eliminar flow; **native `<input type="time">` fields don't respond to a normal triple-click-then-type or a colon-formatted string** — browser-automation testing this session found that typing digits without colons (`"0830"`) directly into a freshly-clicked time input works, triple-click instead selects just the AM/PM segment; worth remembering for testing any future native time/date input in this codebase). `compartir-calendario-sheet.tsx` (invite-by-username, same shape as `compartir-sheet.tsx` for apuntes minus the read/edit permission distinction — a calendar share is just "can see my blocks" or not). `cruce-calendarios.tsx` (the merge view: a checkbox row of everyone eligible — self always included and can't be deselected below one person, since "free for nobody selected" is meaningless — filtering an already-fetched flat block list client-side, no extra round trip per selection change, plus the free-ranges-as-text block underneath the grid).

**CAPTCHA** (`src/components/auth/turnstile-widget.tsx`, new): Cloudflare Turnstile chosen over hCaptcha specifically because this app's actual bot risk (someone scripting fake-domain signups past the existing `@pucp.edu.pe` trigger) is well-served by Turnstile's near-invisible "managed" mode, and it has zero enterprise-tier gating unlike hCaptcha. The widget itself is a `forwardRef` component exposing an imperative `reset()` (Turnstile tokens are single-use; a failed auth attempt must get a fresh one before retrying, not resubmit the consumed token), loads `challenges.cloudflare.com`'s script via `next/script` with `strategy="lazyOnload"` only inside whichever auth form is actually mounted (never in the root layout, so the anon-visible Comunidad feed never loads it), and renders nothing at all when `NEXT_PUBLIC_TURNSTILE_SITE_KEY` is unset. **That last part is the safety mechanism that kept this from being a breaking change**: `login-form.tsx`/`signup-form.tsx`/`recuperar-form.tsx` each compute `captchaRequerido = Boolean(process.env.NEXT_PUBLIC_TURNSTILE_SITE_KEY)` and only disable their submit button on a missing token when that's true, so with no site key configured (today's state), every auth flow behaves exactly as before, verified live by logging in normally post-change. `supabase/config.toml`'s new `[auth.captcha]` block is shipped with **`enabled = false`**, same precautionary pattern as `[auth.external.google]`: a real (not empty) `secret` is required before flipping it, since an empty secret with `enabled = true` would make GoTrue reject every signup/login/recover attempt outright, not just leave the widget cosmetically broken.
