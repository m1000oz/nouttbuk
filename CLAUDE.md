## Product summary

Nouttbuk is a note-taking app for university students that combines a private, per-subject note library with an academic community feed. The single core mechanic is that every note (`apunte`) has a visibility level set individually: `private` (owner only), `group` (owner + invited collaborators with `read`/`edit` permission), or `community` (publishes to a public feed, readable without login; this is the growth/SEO hook and must never be regressed). Reactions and saves on community posts are per-user rows, not global counters.

MVP is scoped to a single university (Pontificia Universidad Católica del Perú): signup is rejected unless the email ends in `@pucp.edu.pe`, enforced both client-side (`src/lib/auth/dominio-institucional.ts`) and at the database level (`private.validar_dominio_institucional()`, wired to two triggers on `auth.users`: `INSERT` in `supabase/migrations/20260817204401_auth_domain_restriction.sql`, and `UPDATE OF email` in `supabase/migrations/20260910135502_extender_validacion_dominio_a_update.sql`, so a signed-in user can't bypass the domain restriction by changing their email after registering). Multi-university support is explicit v2.0 scope (see `STACK.md`).

## Stack

Next.js 16 (App Router, TypeScript) + Supabase (Postgres/Auth/Storage/Realtime) + Tailwind CSS v4 + shadcn/ui (`base-nova` style, over `@base-ui/react`, **not** Radix) + Tiptap v2 (editor; pinned below v3 because `@liveblocks/react-tiptap` requires Tiptap v3 and this project uses a manual Yjs integration instead, see the Liveblocks note below) + Liveblocks (`@liveblocks/client`/`react`/`yjs`/`node`, real-time co-editing for `group`-visibility notes with `edit` permission) + Motion (motion.dev, everyday micro-interactions) + anime.js v4 (a few signature moments, e.g. the Comunidad hero) + jsPDF (client-side CV PDF generation, dynamically imported) + Cloudflare Turnstile (CAPTCHA on signup/login/recover, live with real credentials both locally and on the cloud project, `enabled = true` in `supabase/config.toml`) + Resend (transactional SMTP for Auth emails, see the Architecture note below) + Phosphor icons (`@phosphor-icons/react`) + Vercel (not yet deployed).

All four `@liveblocks/*` packages must be pinned to the exact same minor version; mixing majors (e.g. `@liveblocks/node@^3` against `@liveblocks/client@2.24.4`) loads two incompatible copies of `@liveblocks/core` and Liveblocks throws a runtime "dupes" error.

The visibility model (`private`/`group`/`community`) is enforced via Postgres **Row Level Security**, not hand-rolled authorization checks in application code. Public feed reads and authenticated writes (react/save/comment/create) are designed as separate query/mutation paths.

## Architecture

**Supabase client pattern** (`src/lib/supabase/`): three separate client factories, standard `@supabase/ssr` split — `client.ts` (browser, used from Client Components and the auth forms), `server.ts` (reads/writes cookies via `next/headers`, used from Server Components/route handlers), `middleware.ts` (`updateSession`, refreshes the session cookie on every request). `middleware.ts` is wired in via `src/proxy.ts` (Next.js 16's replacement for the old `middleware.ts` convention at the project root) — it only refreshes cookies, it does not redirect; route protection happens in each gated page, not centrally.

**Route structure** (`src/app/`): a `(shell)` route group holds the four nav destinations behind one shared layout. `(shell)/layout.tsx` is a Server Component that reads the session once (`auth.getUser()` + a `profiles` lookup) and passes it as a plain prop to `AppShell` (`src/components/nav/app-shell.tsx`, a Client Component that owns nav state and the auth modal). Deliberate decision: `(shell)/page.tsx` (`/`) is the public Comunidad feed with **no auth check**, so it can never accidentally end up gated behind a login wall — this is the SEO/growth-hook route from the product rules above. `/inicio`, `/apuntes`, `/perfil` are Server Components that call `redirect("/?login=1")` when there's no session; `AppShell` reads that query param in an effect (keyed on `pathname`, not mount, since a server-side redirect during a client navigation reuses the existing shell instance instead of remounting it) and auto-opens the login modal.

**Design tokens** (`src/app/globals.css`): the Tailwind v4 `--radius-*` scale is *not* derived from a single multiplier — cards/dialogs/sheets need 26px (`--radius-xl`) and buttons/inputs/selects need 14px (`--radius-lg`) simultaneously, which a single-base chain can't produce, so each step of the scale is set to an explicit value. Colors follow DESIGN-SYSTEM.md's Indigo/Teal/Slate tokens with distinct light/dark values (not auto-inverted).

**Icons**: `@phosphor-icons/react`'s default export needs a client boundary (it isn't RSC-safe); the package ships a separate `@phosphor-icons/react/dist/ssr` entry that is. Use the plain import inside Client Components (shadcn-generated `src/components/ui/*` and anything under `src/components/nav/`, `src/components/auth/`), and the `/dist/ssr` import inside Server Components (the gated route pages in `src/app/(shell)/*/page.tsx`).

**shadcn/ui components** (`src/components/ui/`): generated via `npx shadcn add <name>` using this project's `base-nova` style (`components.json`, `iconLibrary: "phosphor"`) over `@base-ui/react` primitives — the generated API shape (prop names, `render` prop patterns, `data-slot` attributes) follows Base UI conventions, not Radix's, even though it looks similar. Check a freshly-generated file's actual output before assuming an API from Radix-based shadcn docs.

**Auth forms** (`src/components/auth/`): `login-form.tsx`, `signup-form.tsx`, `recuperar-form.tsx` are composed inside `auth-modal.tsx` (a fully controlled `mode`/`open` component, no internal state), all reachable from `AppShell`. Supabase Auth error messages are normalized to Spanish copy in one place, `src/lib/auth/mapear-error-auth.ts` (tested in `tests/mapear-error-auth.spec.ts`), rather than string-matched inline in each form. Signup passes `nombre`/`usuario`/`carrera` via `signUp({ options: { data: {...} } })`; it never inserts into `profiles` directly, that row is created by the `handle_new_user` DB trigger. **Signup with email/password now requires a 6-digit code, Google signup does not** (`enable_confirmations = true`, added 2026-09-10, see "Current status"): `signup-form.tsx` owns an internal `paso: "datos" | "verificar"` state (not a separate `AuthModalMode`, same pattern `recuperar-form.tsx` already uses for its own post-submit state) rather than closing the modal on `signUp()` success. It checks `data.session` from the `signUp()` response, not just the absence of an error, since with confirmations required a successful call returns a user but no session until the code is verified (`supabase.auth.verifyOtp({ email, token, type: "signup" })`, which does return a session on success and is what actually calls `onSuccess()`). `supabase.auth.resend({ type: "signup", email })` powers "Reenviar código" and, like `signUp`/`signInWithPassword`/`resetPasswordForEmail`, requires a captcha token, confirmed against the real local `/auth/v1/resend` endpoint, not assumed; the single `TurnstileWidget` instance is shared across both steps (each early-return branch mounts its own copy, which naturally issues a fresh token when switching steps, same as the existing `reset()` call already used after a failed submit).

**Auth email templates and SMTP** (`supabase/config.toml`'s `[auth.email.smtp]` + `[auth.email.template.<type>]` blocks, `supabase/templates/*.html`): production Auth emails (confirmation, recovery, magic_link, invite, email_change) send through Resend's SMTP relay instead of Supabase's default low-volume sender, and render one shared branded HTML system (centered card, table-based button, no external image since the site isn't deployed at a stable URL yet) instead of GoTrue's plain-text default. `content_path` in these config blocks resolves relative to the **project root** (wherever the `supabase` CLI runs), not relative to `config.toml`'s own directory, so paths must read `./supabase/templates/<name>.html`. Domain deliverability (SPF/DKIM/DMARC for `pandatomic.com`) lives in Resend + the domain's DNS host (Vercel), not in this repo. Editing a template requires `supabase stop && supabase start` locally and `supabase config push --linked` for the cloud project to take effect, same as any other `[auth]` change.

**Password recovery redirect chain**: `recuperar-form.tsx` calls `resetPasswordForEmail` with `redirectTo: ${origin}/auth/callback?next=/actualizar-contrasena`. `src/app/auth/callback/route.ts` reads that `next` query param and redirects there after exchanging the code for a session, defaulting to `/perfil` when `next` is absent or isn't a same-origin relative path (open-redirect guard, rejects anything starting with `//` or an absolute URL). `/actualizar-contrasena` (`src/app/actualizar-contrasena/page.tsx`) is a gated Server Component (`redirect("/?login=1")` with no session) rendering `ActualizarContrasenaForm`, which calls `supabase.auth.updateUser({ password })`. Both password fields (login, signup, and this page) share one component, `src/components/auth/campo-contrasena.tsx` (show/hide toggle, inline validation error).

**Auth gate outside the shell's redirect-based flow** (`src/components/nav/auth-gate.tsx`): `AuthGateProvider`/`useAuthGate()` wraps the shell's `<main>`, reusing `AppShell`'s existing `abrirAuth("login")` closure. Gated *pages* (`/inicio`, `/apuntes`, `/perfil`) use the `redirect("/?login=1")` + query-param mechanism described above, but content that's optionally-authenticated on an otherwise-public page (Comunidad's reaccionar/guardar/comentar) can't rely on that, since the page itself never redirects. Any component under the shell can call `useAuthGate().abrirLogin()` to open the login modal from wherever it's rendered.

**Aggregate counts blocked by RLS** (`get_publicacion_counts`, `get_perfil_stats`, migrations in `supabase/migrations/`): when a screen needs a count across *other* users' rows that RLS won't let the caller read directly (e.g. reactions received on your own publications, or public reaction counts for `anon`), the pattern is a narrow `security definer set search_path = '' stable` SQL function living in `public` (not `private`, which is reserved for internal RLS-policy helpers), granted only to the roles that actually need it (`anon, authenticated` for feed-facing counts, `authenticated` only for own-profile stats — never bare `grant ... to public`). Don't reach for client-side joins or loosen RLS instead.

**Sheet vs. full-screen overlay**: two distinct overlay patterns, chosen by how much the screen holds, not by how it's reached. Small single-entity edits (`carpeta-sheet.tsx`, `editar-perfil-sheet.tsx`) use `Sheet`/`SheetContent(side="bottom")` from `src/components/ui/sheet.tsx`, with local `open`/`cargando`/`error` state and `router.refresh()` on success. Full destinations (`apunte-editor.tsx`, `detalle-publicacion.tsx`) render a plain `fixed inset-0 z-50` div from a normal route inside `(shell)`, instead of a nested layout, so they cover the sidebar nav without a second route tree.

**Recurring gotchas**: Tiptap's `useEditor()` needs `immediatelyRender: false` (otherwise an SSR hydration mismatch, since ProseMirror needs the real browser DOM). Base UI's `Select` needs an `items` prop (not just `SelectItem` children) or the closed trigger shows the raw value instead of the item's label; its popup width is `w-max min-w-(--anchor-width) max-w-[min(90vw,28rem)]` in `src/components/ui/select.tsx` specifically so a long, not-yet-selected option can't get clipped, don't reintroduce a hard `w-(--anchor-width)` lock there. A component that seeds `useState` from an optional prop needs a `key` tied to that prop's identity, or it goes stale when the prop changes without the component unmounting. A PostgREST embed between two tables with more than one relationship path (e.g. `apuntes`↔`profiles` via both `autor_id` and `colaboradores`) needs the explicit FK name (`profiles!apuntes_autor_id_fkey`), or the query silently returns `PGRST201`. RLS policies alone aren't enough for a new table: Postgres checks table-level `GRANT`s first, so every RLS-protected table also needs a matching grant (see `supabase/migrations/20260818053857_table_grants.sql`), and this must be considered explicitly even for the `anon` role on a table `anon` has no RLS policy on at all, otherwise a missing grant surfaces as a hard permission-denied error instead of the intended RLS-driven empty result (hit twice in this project's history, on `feedback` and once earlier, get it right on the first migration draft for any new table). A flex container with no explicit `align-items` defaults to `stretch`, which silently caps a `min-h-[...]`-only child's height at the container's own computed height instead of letting it grow with content (bit the editor's A4 "hoja" once); add `items-start` when a child should size to its content. pgTAP's `throws_ok(sql, errcode, description)` matches its third argument against the actual Postgres exception message, not a free-text description, unless a 4th argument is passed. There is no admin role anywhere in this app: status/moderation changes (`feedback.estado`, reviewing rows in `reportes_publicacion`/`reportes_comentario`) are done by hand via SQL or Supabase Studio, not a built UI, by design. Never combine two related pieces of text with a "·" middle dot or an em dash, both were removed everywhere on purpose (see the Language rule below), prefer a stacked two-line layout, a thin `bg-border` vertical rule, or a `Badge` instead. Any future `@liveblocks/*` package addition must be pinned to match the other four (`client`/`react`/`yjs`/`node`, currently all `2.24.4`) or Liveblocks throws a runtime "dupes" error. Any clickable control inside the note editor (toolbar button, menu trigger) that runs a Tiptap command needs `onMouseDown={(e) => e.preventDefault()}` in addition to its `onClick`: a plain `<button>`'s native `mousedown` behavior moves DOM focus to the button before `click` fires, which blurs the ProseMirror `contenteditable` for one tick, which can hide/reposition anything whose visibility or placement depends on `view.hasFocus()` or on measuring the document's current layout (hit repeatedly across editor sessions: the old BubbleMenu, and separately any control that changes something reflow-affecting like alignment or block style) — preventing the mousedown default keeps focus on the editor the whole time, so this class of bug can't happen at all, not just less often. Base UI's `Menu`/`Dialog` (and anything built on them, like `DropdownMenuContent`/`DialogContent`) portal to `document.body` by default, escaping any scoped CSS-variable override like `.apunte-editor-overlay`'s atelier tokens; both components now accept an optional `container` prop (a `RefObject<HTMLElement | null>`) threaded straight to the underlying Base UI `Portal`, so a component rendered inside a themed subtree can keep its popovers themed too instead of needing a hand-copied `!important` override class (see `editor-menu-bar.tsx`'s `overlayRef` for the pattern) — the older Select/Sheet-based popovers elsewhere in the editor header still don't pass this prop and still escape to the app's ambient theme, a known, accepted gap, not something this pattern retroactively fixed. A CSS rule that only redefines custom properties (`--foreground`, etc.) on a scoped class does **not** by itself recolor descendant text that relies on plain inheritance: a property inherits its *already-computed* value, not the `var()` expression, so an ancestor further up the tree (like `<body>`'s own `text-foreground`) can "win" for any descendant that never declares its own `color` — the fix is a `color: var(--foreground)` (or equivalent) declaration on the scoping class itself, not just the custom-property redefinitions (bit `.apunte-editor-overlay` itself, several header icons were invisible for two iterations before this was caught). `requestAnimationFrame` is not a safe way to schedule a non-animation layout recalculation triggered by content changes: rAF only runs when the browser is about to paint a new frame, which some rendering contexts (a backgrounded tab, an automation-controlled browser) can delay indefinitely or never do at all, silently freezing whatever depended on it (bit `pagination-extension.ts`'s `medirYDecorar`, confirmed via a bare rAF call that never fired for several seconds in a browser-automation session); `setTimeout(fn, 0)` runs unconditionally instead and is the correct tool for this class of work regardless of the testing-environment quirk that surfaced it. ProseMirror's `view.posAtDOM(node, 0)`, where `node` is a top-level block's own DOM element, returns the position just *inside* that node (before its first character), not the position before the node as a sibling — a `Decoration.widget` placed there renders as that node's own first child instead of a preceding sibling div; the fix is `posAtDOM(parentDom, childIndex)` (the position at that child-offset of the parent), which lands genuinely between siblings (see `pagination-extension.ts`'s page-break spacer). A `Decoration.widget` from a previous render pass is still a real DOM element until the next `dispatch` replaces it: any measurement loop over `dom.children` that doesn't explicitly skip old widgets will re-count their height as if they were content on every later recalculation, corrupting any threshold-based logic (page/chunk boundaries, etc.) for the second and later thresholds even after the first one works correctly; separately, an accumulator being compared against a "pure capacity" threshold must never have the computed gap/overflow amount folded back into itself, or every threshold after the first is reached too early. A percentage width (`w-full`) on an element whose parent has no definite width of its own (sized via CSS shrink-to-fit) contributes nothing to that parent's intrinsic-size calculation per spec; with too little other content to establish a natural width, the whole chain can collapse to just the innermost padding — give the child a definite pixel width instead (with `maxWidth: "100%"` for responsive shrink) when this pattern is unavoidable (bit `hojas-editor.tsx`'s page container on a brand-new, still-empty note). When a screenshot contradicts a direct `getComputedStyle`/DOM check in this environment, trust the computed check (or re-capture via `zoom`) before concluding something is visually broken — the plain screenshot action has been observed serving a stale cached frame for a region across several consecutive calls. Pasting plain text with single line breaks (no blank line between them) produces one paragraph with internal `hardBreak` nodes, not separate paragraphs, in both of ProseMirror's clipboard paths (plain-text fallback and HTML, since many real sources represent their own line breaks as `<br>`) — a block-level pagination scheme that can only break between whole top-level nodes then has to push that entire multi-line paragraph whole when it doesn't fit, wasting up to its full height; `clipboardTextParser` only fires when the clipboard has no HTML at all, so it's the wrong hook to normalize this — `editorProps.transformPasted` (see `src/lib/tiptap/pegar-lineas-como-parrafos.ts`) is the one hook ProseMirror always calls regardless of which path produced the slice, and both `editor-estatico.tsx` and `editor-colaborativo.tsx` configure `editorProps` separately, so a paste-behavior fix needs to be wired into both, not just one. A ProseMirror plugin's `update()` view hook fires synchronously inside `editorView.dispatch()`; if a "recalculation scheduled" flag is reset to `false` before that `dispatch` call (instead of after), the hook's own re-entrant call sees the flag already clear and reschedules an extra, usually-redundant pass on every single content change — reset debounce flags like this only once the dispatch that they guarded against has actually completed. An accumulator being compared against a page-capacity threshold must be reset to 0 at every successful break, not left as a running total compared against `paginaActual * alturaUtil`: since almost no paragraph ends exactly at the page boundary, each page's small leftover space gets added again into the next break's gap calculation, and the next, compounding additively with every page (confirmed algebraically and with a numeric simulation: exact on the first break, then growing without bound) — invisible on a 2-3 page note, visible by page 4-5 as the last line before a break sitting flush against the bottom edge with no margin, and a too-large blank gap at the top of the next page (`pagination-extension.ts`'s `medirYDecorar`, found 2026-09-08 from a real multi-page stress-test note); comparing against a single `alturaUtil` and zeroing the accumulator right after pushing each `puntoDeCorte` fixes it at the root instead of shrinking the error. This same drift was very likely also the cause of a reported "flickers terribly at the end of a page": content sitting near a boundary that had already drifted close to the (wrong) threshold is far more likely to flip in/out of overflow across successive recalculation passes, each one re-dispatching new decorations, which is what a rapid flicker looks like; fixing the drift removes the persistent near-boundary condition, though this hasn't been re-verified live in a browser (no browser-automation tool was available in that session). `Paginacion`'s whole-node-push design has a structural blind spot the drift fix doesn't touch: a single paragraph/heading that by itself grows taller than one full page can never be resolved by pushing it (pushing doesn't help, it still won't fit on the next page either), so it just flows straight through the visual gap between pages uncontrolled — confirmed as the root cause of a 2026-09-08 report that the gap between pages was "space where you can write text that isn't visible" (`.pila-hojas .tiptap-content`'s hardcoded near-black text color, meant for the paper background, is nearly invisible against `.lienzo-editor`'s dark atelier background when content spills into the gap in oscuro mode). A pure CSS/decoration fix (lighter gap background) was considered and rejected by the user as not addressing the actual problem (content genuinely flowing uncontrolled, not just a contrast issue). The real fix (Pass 14, `pagination-extension.ts`) dispatches a genuine, permanent `state.tr.split(pos)` — exactly what pressing Enter does — when a paragraph/heading's own height exceeds `alturaUtil`, finding the split position via `editorView.posAtCoords` (the same method `hojas-editor.tsx`'s `manejarClicPila` already uses for click-to-cursor). **This was deliberately NOT implemented as a reversible view-only split** (split now, un-split on the next recalculation, to fake a Google-Docs-style visual break without touching saved content): investigated and confirmed unsafe for the collaborative editor specifically, because `y-prosemirror`'s `ySyncPlugin` syncs *every* transaction where `tr.docChanged` is true to Yjs and to every collaborator, with no meta-flag or other mechanism (in this codebase or in y-prosemirror itself) to mark a transaction as local-only/excluded from sync — a temporary split would be broadcast and land in the Yjs history before it could be reverted, risking real corruption under concurrent edits near a page boundary. A genuine, permanent split sidesteps this entirely (it's a real, intentional edit like any other, synced normally, no revert dance), at the accepted cost of actually restructuring the user's paragraph into two real paragraph nodes (permanently — resizing the page later doesn't undo it). Scoped to `paragraph`/`heading` node types only and gated on `editorView.editable` (this extension is also used read-only in `detalle-publicacion.tsx`'s public Comunidad view, which must never mutate a post's content just from being viewed). A long paragraph converges to page-sized chunks over several recalculation passes (one `tr.split` per pass, each retriggering the plugin's own `update()` hook), capped by a dedicated `MAX_DIVISIONES_ENCADENADAS` counter (separate from `pasadasEncadenadas`, which only tracks decoration-signature convergence) so a pathological case degrades safely instead of looping forever. Verified with a numeric simulation of the convergence (bounded passes, no leftover chunk taller than one page); **not verified in a real browser** (no browser-automation tool available that session) — ask the user to type one long unbroken paragraph past a page boundary in both a private and a collaborative note and confirm it splits cleanly with nothing left in the gap, and that collaborators see the same result. A Tiptap extension's `addCommands()` (unlike `addAttributes()`, which already does this correctly everywhere in this codebase) does **not** merge with its parent's commands by default: `TextStyle.extend({ addCommands() { return { ...unrelated } } })` (as `font-size-extension.ts`'s `FontSize` did) silently drops every command the parent defined, including `removeEmptyTextStyle` — and since `FontSize` is the only actual instance of the `textStyle` mark in this project's schema (Color/FontFamily only add global attributes to it, they don't redefine it), that command then doesn't exist anywhere in the editor's command map at all. This broke three real toolbar buttons in production terms (not just theory): "Predeterminada" in `SelectorFuente` (`unsetFontFamily`), "Predeterminado" in `SelectorTamano` (`unsetFontSize`), and "Quitar color" in `SelectorColor` (`unsetColor`) all threw `removeEmptyTextStyle is not a function` on click and silently did nothing (confirmed live via the browser console, 2026-09-09). Fixed by adding `...this.parent?.()` to `FontSize`'s `addCommands()`, same pattern `addAttributes()` already used. **A `src/components/ui/*` component that uses a React hook or context (like `Button` wrapping `@base-ui/react/button`) needs its own `"use client"` directive even if every other file in that directory already has one.** `button.tsx` was missing it and worked anyway for months, purely because every existing call site happened to sit inside some other Client Component's boundary; it only broke (`createContext only works in Client Components`) the first time a Server Component (`src/app/not-found.tsx`) imported `Button` directly, crashing the entire route (and, via the shared error boundary, every route). Don't assume a `ui/*` file is safe to import from a Server Component just because it's in that directory, verify it has `"use client"` at the top, or add one, before relying on it there.

**Security headers** (`next.config.ts`'s `async headers()`): `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy` apply to every response. Deliberately no `Content-Security-Policy` yet, a CSP tight enough to matter risks breaking the Turnstile iframe, Google OAuth redirect, or the Liveblocks WebSocket, and hasn't been scoped/tested.

**The toast system** (`src/components/ui/toast.tsx`) is a hand-written adaptation of the shadcn `base-nova` registry's `toast` component (the CLI's `npx shadcn add toast` hung indefinitely once and was worked around by hand-copying the registry output), it exports a singleton `toast` object any Client Component can call (`toast.add({ title, type })`) without a provider, only the `<Toaster>` mounted once in the root `layout.tsx` needs to exist for it to render. Reuse this pattern for success/error feedback on new mutations rather than inventing another notification mechanism.
